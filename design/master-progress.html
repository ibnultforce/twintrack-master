TwinTrack Master Progress

What has been added to the Master module so far, and what comes next. Updated whenever the code changes.

Last updated 19 November 2026. The redesign (phases 1 to 6), the Project management module (formerly Tasks) and the HR data models are not committed yet.

Where things stand

The Master backend is finished for now. Besides signing in and managing their own account, admins can now manage people, roles, special privileges and modules, and read the activity log, all through the API. The portal and admin console now run on these routes in the browser. What remains of step 6 is turning the demo scenarios into tests and checking the cookie across real subdomains. The 7 remaining routes wait for the Employee module. A redesign on profiles, an org tree and shared records has started: all six phases are built: the org tree, profiles with permission sets, the record base, sharing, field-level security and custom objects. The Project management module (called Tasks until 13 November) is complete in the API and its own frontend, with everything from the old app: points, logins with one-time codes, files, incentives, flags, billing, health and team reports, exports and MCP tools. On 11 November, Master gained everything it owns from the old TwinTrack app: emailed set-password links through Resend in place of temporary passwords, employee numbers, profile photos, online status, a directory, clients, deleting people added by mistake, personal API tokens, OAuth for connectors, an MCP endpoint, and a development-only "Log in as". The rest of HR has its data models, ready for the old app's data; its APIs come next.

What has been added

Signing in and staying signed in

  • Access tokens last 15 minutes and hold only who you are. Permissions are read from the database on each call, so a role change applies on the next request.
  • Refresh tokens sit in an HttpOnly cookie that JavaScript can't read, and only their hashes are stored. Each one is replaced when it's used.
  • A session ends after 7 days without use, and after 30 days regardless.
  • Two open tabs can refresh together, thanks to a 10-second grace period.

Checking access on every call

  • Each route declares its access, and the matching checks attach automatically, so a protected route can't go live without them.
  • Each call checks the token's signature and expiry, that the session is still open, and that the account is active. Signing out or being deactivated takes effect at once, even with a token that hasn't expired.
  • A person's profile and the permission sets they hold combine into one set of permissions, and the widest scope wins. A set the module no longer has, or a module that isn't loaded, grants nothing.
  • Someone with a temporary password can only see their profile, change the password or sign out until they've changed it.

My account

  • People can read their profile and change their own name. Job details such as title stay with HR, and a request trying to change anything else is refused.
  • Changing a password needs the current one, at least 8 characters for the new one, and ends the person's other sessions. Repeated wrong guesses get blocked.
  • People can list the modules they can open, and see what they're allowed to do in each.

Managing people

  • Admins can list, search, add and edit people. Lists come in pages, and a request trying to set a field such as super admin is refused.
  • Nobody is given a password. New people and password resets get a one-time link by email, sent through Resend. Only a hash is stored, a newer link replaces an older one, and using it signs the person out everywhere.
  • Each person gets the next employee number. Admins can change it, and it stays unique.
  • Someone added by mistake can be deleted, but only if they never signed in and no module's records name them. Everyone else is deactivated.
  • Deactivating someone signs them out everywhere, and reactivating them doesn't bring an old session back.

Profiles and permission sets

  • Each person has one org-wide profile, which sets their baseline in every module. Only Master admins build profiles and give them.
  • Permission sets are named bundles in one module, given on top of the profile. Module admins give them, and giving one needs a reason.
  • Nobody can build a profile or set beyond their own access. A change applies on the person's next request, even with a token they already hold.
  • HR access managers can change HR permission sets only.
  • Nobody can change their own access. Only a super admin can edit, deactivate or reset a super admin, so an admin can't take over that account.
  • The Profiles screen lists who holds each profile, with their role, status and the modules it gives them, and a Remove button wherever the viewer may take the profile away.

Modules and the activity log

  • Admins can import a module's manifest, and every problem in an invalid one is listed. Master can't be replaced or removed through the API.
  • Removing a module ends access from it. People's roles stay on record and work again if it's imported again.
  • Every admin change writes to the activity log in the same transaction, with who did it and what changed. Passwords are never included.

Protection

  • Reusing an old refresh token ends the whole session and records it in the activity log.
  • Login, refresh and logout refuse any address not on the allow-list. CORS alone would still have let those requests run.
  • Failed logins are limited per address, with counts shared between API instances. A wrong password and an unknown email get the same answer, in about the same time.
  • Tokens and cookies are removed from the logs.
  • The API won't start without a signing secret of at least 32 characters, and production refuses a cookie that isn't HTTPS-only.

From the old app (11 November)

  • Profile photos, with initials when there is none. People change their own; someone else's needs user.update.
  • Online status from a heartbeat every 45 seconds, shown only where the viewer's presence.read scope reaches.
  • A directory of active colleagues for everyone signed in.
  • Clients, shared by every module, with history and field access. Made inactive, never deleted.
  • Personal API tokens and OAuth connected apps, both acting as their person, through an MCP endpoint with Master's tools. Other modules add their own tools.
  • "Log in as" on a person's page, for super admins in development only. A banner shows it, and it is logged.
  • Confirming your password before something sensitive, for salaries later.

Project management module (called Tasks until 13 November)

  • Projects with a lead and members. Tasks go only to the lead or a member, and someone with open tasks can't be removed.
  • Each task gets a number such as T-00102 that is never reused. It moves from to-do through work, QA and approval, can be reverted with a reason, and can be cancelled unless it's done.
  • Separate timers for the assignee and for QA, which can be paused and resumed, and the approver settles the hours.
  • Access comes from permission sets and the task's own people, never from role names. Only the assignee runs the timer, only the QA person runs QA, and nobody approves their own work.
  • QA hours are protected fields. Comments are kept for good, and tasks can link to each other.
  • Career points: 50 per approved hour of work or QA, less 5% of a task's points each time it is reverted. A revert can give the fix to someone else.
  • QA tasks record their own pass or fail. QA can't start without a QA estimate. Tasks can be flagged, marked not billable, and have their actual hours corrected.
  • Search, filters, sorting, totals and CSV export. Project health and team reports.
  • Shared project logins, encrypted, showing the current one-time code but never its secret.
  • Files on tasks, up to 5 GB a task, sent straight from the browser to Cloudflare R2, or to the local disk in development.
  • Monthly incentives from the hours a team lead led, at each person's rate, and one-off project incentives. A paid month is frozen.
  • MCP tools to list, create, update, reassign and hand over tasks by name.

Keeping the project consistent

  • Manifests live in twintrack-master/manifests/, one per module: Master, HR, Project management and Demo.
  • A test fails if any module's route table and its manifest disagree about which routes are built or who can use them.
  • A test fails if a route has no Postman request.
  • npm run seed now requires SEED_PASSWORD, in place of a password written into the code.

Known limits

  • Every permission check reads the session, user and module from the database. That's what makes changes apply at once, at the cost of a few extra queries per call.
  • A stolen refresh token that has just been replaced still works for up to 10 seconds. That's the cost of supporting two open tabs.
  • The login limit counts per address, so attacks spread across many addresses get past it.
  • Permission sets have no end date, and the reason for giving one is kept only in the activity log.
  • A database seeded before profiles keeps the old assignments and privileges fields, which now grant nothing. Run npm run seed to reload it.
  • Only Master admins can give profiles. A module admin can't change someone's profile, only their sets in that module.
  • A real Resend key hasn't been tried yet. Without one, links go to the backend log, which only development allows.
  • People seeded before employee numbers have none until an admin gives them one. New people get the next number.
  • OAuth client secrets need ENCRYPTION_KEY. Without it in development, a random key is used, so apps must connect again after a restart.
  • A production database has no way to get its first super admin or the Master manifest, because the seed refuses to run in production and the API can't create either.
  • People created before the org tree have no orgRoleId. They see only their own records and direct reports until someone gives them a place in the tree.
  • The admin console has no screen for the org tree yet. It is managed through the API, Postman and the test page.
  • Anyone with user.update can place people below their own org role, which widens what they see. That is by design, as with assigning a manager, but the role should go only to trusted admins.
  • Payroll uses one HR salary amount per person. The old app's breakdown into basic pay and allowances waits for HR.
  • Invoice documents carry no company logo yet.
  • R2 storage hasn't been tried with a real bucket. The bucket needs CORS that allows PUT from the frontends and exposes ETag.
  • The Project management frontend has no automated tests in the repo; the Chrome run was a one-off.
  • Approving a task whose QA result is fail is allowed. The approver is expected to revert it instead.

10 November 2026: record base (redesign phase 3)

  • Salaries and projects now carry who created and last changed them, a version number, and soft delete. One shared plugin adds these, and keeps deleted records out of every query unless asked for.
  • Each change writes to the record's history in the same transaction, for the fields the manifest lists in trackedFields. The history holds values such as amounts, so it follows the same reach as reading the record. The activity log still leaves amounts out.
  • Sending the version you read with an edit refuses it with 409 version_conflict if someone changed the record since.
  • Tests, Postman, the test page, the API docs and the README cover it. HR and Project have no frontend yet, so there is nothing new in the console.

10 November 2026: profiles and permission sets (redesign phase 2)

  • Roles and special privileges are gone. Each person now has one org-wide profile for their baseline in every module, plus any number of permission sets, each belonging to one module.
  • New routes: /access-profiles to list, add, change and remove profiles, and /permission-sets in place of /roles. PUT /users/:id/permission-sets replaces PATCH /users/:id/roles and PUT /users/:id/privileges, and PATCH /users/:id takes profileId. The grantable route is removed.
  • Only Master admins give profiles. Module admins still delegate, by giving their module's permission sets. Nobody can build a profile or set beyond their own access, and giving a set needs a reason.
  • Manifests now hold permissionSets. The old roles and grantable fields are refused. Master is at 2.6.0, HR 1.6.0, Employee 0.9.0 and Project 0.3.0.
  • The console has new Profiles and Permission sets screens, a profile picker on each person, and permission sets in place of roles everywhere. Adding a person now asks for their place in the org tree, which phase 1 had left out.
  • Tests, Postman, the test page, the API docs and the README cover it.

10 November 2026: org tree (redesign phase 1)

  • New org roles form a tree with exactly one root. Four routes under /org-roles list, add, rename or move, and remove them. Moving a role moves everything below it, and circles are refused.
  • Adding a person now needs an orgRoleId, and it can be changed afterwards. Nobody but a super admin can move themselves or the role they hold.
  • team scope now reaches direct reports plus everyone in the org roles below, at any depth, for HR salaries and projects. The tree passes on what people can see, never what they can do. Peers in the same role don't see each other's records.
  • The Master manifest is at 2.5.0, with a new orgRole resource. The seed adds a sample tree in seed/org-roles.json that matches the existing reporting lines.
  • Tests, Postman, the test page, the API docs and the README cover it.

10 November 2026: projects can be created

  • The Project Management module has a Project model, with an owner, members and a status, and routes to list, read and create projects.
  • project.read is scoped. own reaches projects you own or work on, team adds your direct reports' projects, and all reaches every project.
  • HR salaries and projects now share one helper for who a scope reaches.

10 November 2026: Project Management module started

  • A super admin can call it right away, and can give it to others from Master by creating a Project role or giving project.read as a special privilege.
  • Postman, the test page, the API docs and the README cover it. The Postman run was not repeated for this change.

9 November 2026: super admins can remove actions in use

  • A super admin can untick any action on a resource. Roles lose it, and an API that needs it can then be used only by super admins. Everyone else still sees actions in use locked.

9 November 2026: actions in use are locked

  • When editing a resource, an action used by an API or role is locked, with what uses it listed. The server's refusal now names those instead of manifest paths.

9 November 2026: separate module permissions

  • On the Modules screen, adding a resource needs module.create, changing a resource or what's grantable needs module.update, and removing a resource needs module.delete.

9 November 2026: separate role permissions

  • Each module now has separate role.read, role.create, role.update and role.delete. Holding role.update no longer lets someone create or delete roles.

9 November 2026: export and confirmed import

  • The Modules screen can export any module's manifest, from a button beside Import manifest.
  • Importing a manifest now asks for your password before anything is saved.

9 November 2026: manifests match the code

  • npm run seed:modules reloads manifests without touching people, and keeps roles created in the app.
  • Manifests now list only built routes and the resources they use. Planned routes, unbuilt resources such as leave and attendance, user.delete and the Account manifest are gone.

9 November 2026: shorter passwords

  • A new password now needs at least 8 characters instead of 12.

9 November 2026: code review fixes

  • Only a super admin can import roles or widen what's grantable. module.update can still narrow it.
  • Role and resource edits read and save in one transaction, so two editors can't overwrite each other, and a role can't be deleted while someone is being given it.
  • A server outage no longer signs people out, switching modules no longer shows the previous module's people, and role names without Latin letters now work.

9 November 2026: no ready-made roles

  • Only the super admin has access now. Every manifest ships with no roles, and the sample people start with none.
  • Each module has its own role.update. A super admin can give it to someone, who can then create and edit roles in that module using only permissions they hold.
  • The Roles screen works from empty and lists the APIs each permission opens. Changing what a module offers now needs module.update.

9 November 2026: Master portal and admin console

  • On Access, choosing a person is now a search box with a dropdown list, backed by a new route that works for module admins too.
  • Added a slim custom scrollbar across the app, in light and dark mode.
  • On Your permissions, each module's list now has a set height and scrolls inside it.
  • The sidebar now stays in place at the window height while the page scrolls.
  • Several special privileges can now be given to one person in a single save, with one reason, using a search box with a dropdown list.
  • Opening the app at localhost now redirects to the address set by the new NEXT_PUBLIC_APP_URL, so sign-in works from either.
  • Built the sign-in, temporary password, module list, permissions and profile screens.
  • Built the Overview, People, Access, Roles, Permissions, Modules and Activity log screens on the real API. Each person only sees what their permissions allow.
  • The new Access screen lets module admins, who can't open People, manage their own module.

9 November 2026: Employee profile, Jasmin and Jack

  • Jack can view his profile but not change it there. Jasmin can give or remove profile.update, or change his role, and it applies on his next request.
